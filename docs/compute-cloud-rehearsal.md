# COMPUTE 리허설 · EC2에서 GCE로 웹 트래픽 전환과 롤백

2026년 11월 6일 08:47:07–08:47:53 KST, 팀 데모에서 로그인한 사용자가 같은 주소를 계속 호출하는 동안 웹 요청을 EC2에서 GCE로 옮긴 뒤 EC2로 되돌렸다. 세션을 확인한 HTTP 요청 **291건이 모두 성공**했다. 기존 WebSocket은 EC2에서 메시지 확인 응답 47건을 받았고, 전환 후 같은 주소로 연 새 WebSocket 두 개는 GCE에서 응답했다.

## 무엇을 옮겼나

```text
테스트 클라이언트 → 고정 주소 (EC2 내부 Nginx)
                       ├─ EC2 웹 ───────────┐
                       └─ GCE 웹 ─ SSH 터널 ─┤
                                           └─ EC2의 PostgreSQL/PgBouncer, Valkey, S3Mock
                                              원본 Worker 2개가 주문 처리
```

- **프로비저닝** · 기존 서울 리전 네트워크에 저장소의 EC2·GCE 모듈로 각각 `t3.medium`과 `e2-medium`을 생성했다. 별도 state의 plan은 생성 8개, 기존 자원 변경·삭제 0개였다.
- **앱 준비** · 양쪽 VM에 같은 데모 이미지를 적재했다. GCE의 COMPUTE 어댑터가 `PREPARE`로 이미지 ID와 설정을 확인하고, `START_SYNC`로 대상 웹을 실행해 HTTP 점검을 통과했다. 검증 버전은 [IaC 6905311](https://github.com/SoftBank-2026-Hackathon-Foxtrot/IaC/tree/690531153c4f3a5d14145b7dc4be500de3ed53c0)과 [demo bc9b691](https://github.com/SoftBank-2026-Hackathon-Foxtrot/demo/tree/bc9b691d174fba855c5aeec822e272b9e7582856)이다.
- **트래픽 제어** · 테스트 실행기가 Nginx 가중치를 바꿨다. 데이터와 Worker는 EC2에서 계속 서비스했다. 팀 트래픽 어댑터·공용 도메인 연동, 관리형 DB·캐시·객체 데이터 이전, 원본 VM 종료 후의 가용성은 후속 검증 범위다.

## 트래픽을 바꿀 때 사용자가 본 결과

한 번 로그인한 뒤 같은 세션으로 `/api/me`를 반복 호출했다. HTTP 200과 사용자 ID를 함께 검사하고 응답 헤더로 처리 위치를 구분했다.

| 설정한 비율 (AWS/GCP) | EC2 응답 | GCE 응답 | 실패 |
|---|---:|---:|---:|
| 100/0 · 시작 | 38 | 0 | 0 |
| 95/5 | 96 | 5 | 0 |
| 50/50 | 27 | 28 | 0 |
| 0/100 | 1 | 51 | 0 |
| 100/0 · 롤백 | 43 | 0 | 0 |

첫 단계 기록 전의 요청 2건을 포함해 총 291건이었다. 지연은 p95 19.3 ms, 최대 94.62 ms였다. 단계는 설정 변경 직후의 시각과 요청 시작 시각으로 나눴다. GCP 100%를 설정한 구간에도 EC2 응답이 1건 관측됐다. 운영 전환에서 원본을 내릴 때는 새 요청의 처리 위치와 기존 연결 종료를 별도로 확인해야 한다.

GCP 전환 구간에 팀 데모의 [check_live.py](https://github.com/SoftBank-2026-Hackathon-Foxtrot/demo/blob/bc9b691d174fba855c5aeec822e272b9e7582856/scripts/check_live.py)를 두 번 실행했다. 첫 실행은 EC2·GCE에 각각 접속했고, 두 번째는 같은 진입점에서 두 연결 모두 GCE에 도착했다. 두 실행 모두 채팅 전달·재접속 이력·로그아웃 후 연결 폐기, 중복 주문 방지, 원본 Worker의 주문 확정과 영수증 조회를 통과했다.

첫 측정에서는 확인 응답의 UUID를 하이픈 없이 비교해 WebSocket 측정기가 시간 초과됐다. 데모와 같은 표준 UUID 문자열로 비교하도록 측정기를 수정한 후 전환과 롤백 전체를 다시 실행했다. 위 수치는 재실행 결과다.

## 정리 확인 · 08:49:58 KST

Terraform이 이번 실행에서 생성한 자원 8개를 삭제했다. 이어서 클라우드 API에서 실행 식별자와 생성 시 기록한 자원 ID로 잔여 수를 조회했다.

| 위치 | 확인한 항목 | 결과 |
|---|---|---|

| GCP | VM, 부팅 디스크, 예약 IP, 방화벽 규칙, 활성 서비스 계정, 이번 OS Login 공개키 | 각 0개 |
| Terraform | 리허설 state의 관리 자원 | 0개 |
